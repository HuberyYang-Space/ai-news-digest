# 架构：为什么长成这样

> 这篇只解释**取舍的理由**。数据流图、目录树、workflow 对照表这些事实描述在
> [README](../README.md#工作原理) 里有唯一一份，本文只做锚点引用，不复制。
> 现役禁令在 [CLAUDE.md](../CLAUDE.md)，不在这里。

## 站点没有记忆，所以 Git 是数据库

RSS 是滑动窗口：高频源的 feed 里只留得住最近几小时的条目。这一条事实决定了整个架构——
**周一再一次性抓「过去 7 天」是抓不全的**，所以不存在「出刊时才联网」这个选项。

可选的解法有三种，选了第三种：

| 方案 | 为什么没选 |
|---|---|
| 接数据库 / KV 存原料 | 要自建或托管一个有状态服务，和「GitHub Pages 纯静态、零运维」的定位冲突 |
| 出刊时抓更长的 feed（`?limit=`、翻页） | 各家 RSS 对历史条目的支持参差不齐，多数根本不提供，可靠性不可控 |
| **每日采集提交进仓库** | 选它：Git 本来就在跑 CI，快照是纯文本、可 diff、可回溯，且天然免费 |

代价是仓库会持续变大（每天一个 JSON 快照），换来的是**快照永久保留**——任何时候都能拿历史
原料重算某一期，这是调选取算法的唯一手段（见 [`selection-algorithm.md`](selection-algorithm.md)）。

## 三段式为什么这么切

采集 → 选取 → 组装的分界线不是随便画的，每条缝都对应一个具体需求：

- **选取（[`src/data/build-issue.ts`](../src/data/build-issue.ts)）被切成纯函数，不碰 I/O。**
  这是为了让 `pnpm rebuild-issue` 成立：调完参数能在真实历史快照上立刻重跑、对比结果。
  如果选取里夹了读文件或发请求，「重算历史期」就要么做不到、要么每次都要重新联网抓一遍。
  本仓库没有测试框架，`rebuild-issue` 就是选取逻辑事实上的回归手段，这条纯函数边界是它的前提。
- **翻译被放在组装（[`src/data/assemble-issue.ts`](../src/data/assemble-issue.ts)）而不是采集。**
  原始方案确实放在采集期（见 [DeepL 翻译决策记录](decisions/2026-07-22-deepl-translation.md)），
  但 14 源 × 每天 × 全量条目会撑爆 DeepL Free 的月额度。挪到出刊期后只翻译入选的那几十条，
  并把结果**冻结进期号 JSON**——于是重建站点永远不会重新翻译。
- **采集（[`src/data/fetch-sources.ts`](../src/data/fetch-sources.ts)）只管抓，不做任何筛选。**
  因为不再花翻译额度，采集可以放开手多抓（`ITEMS_PER_SOURCE` 从 5 提到 20），把「留什么」
  的判断全部推迟到出刊期。原料抓得越全，事后调算法的空间越大。

## 渲染：为什么是 vite-ssg 多页而不是 SPA

核心约束是**期数会无限增长**。如果按 SPA 做，要么把全部期号打进一个 bundle（第 52 期时首屏
要下载 52 期内容），要么在运行时按需 fetch JSON（就不再是纯静态，且 GitHub Pages 上多一层
网络往返）。

vite-ssg 多页模式两个都避开了：它对每条路由单独调一次 SSR 入口，并把 `initialState`
序列化进**那一条路由自己的 HTML**。所以 [`loadPageData()`](../src/data/load-content.ts)
按路由只装载本页数据，期数再多也不会进别的页面。

这条性质是**跨期导航刻意用 `<a>` 而不是 `RouterLink`** 的原因：每个页面都已完整预渲染，
整页跳转是零额外请求的；换成客户端路由反而要在运行时去 fetch 目标期的 JSON，把上面这个
性质亲手破坏掉。

同理，[`CategoryNav.vue`](../src/components/CategoryNav.vue) 是锚点目录而不是筛选器——
一期是一次完整的阅读，点分类应该滚过去，而不是把其余内容藏起来。

## CI 为什么拆成三条 workflow

三条流水线的触发条件、权限、频率各不相同（对照表见
[README「定时任务的执行机制」](../README.md#定时任务的执行机制)），合并的话会出三个问题：

1. **权限过宽**：部署需要 Pages 和 `id-token: write`，采集只需要 `contents: write`。
   合并意味着每天的采集任务都带着部署权限跑。
2. **构建回环**：写内容的任务会 commit，commit 又会触发构建——GitHub 对 `GITHUB_TOKEN`
   推送的 commit 不触发 workflow 这一点挡住了它，但拆开之后即使那条机制失效，
   `paths-ignore: content/**` 还是第二道保险。
3. **失败的代价不同**：采集失败只是当天少一份原料，部署失败是站点不更新。
   混在一起会让「今天有个 RSS 源挂了」和「站点炸了」变成同一条红色通知。

出刊排在采集之后一小时，是为了确保用得上当天早上那份快照。
