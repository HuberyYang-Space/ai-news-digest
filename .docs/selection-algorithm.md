# 选取算法：参数从哪来，怎么改

> 算法**是什么**（IDF 加权 Jaccard、阈值 0.18、排序依次看哪些字段）在
> [README「内容怎么选」](../README.md#内容怎么选) 里有唯一一份描述。
> 这篇讲的是那些数字**怎么量出来的**，以及要改它们该走什么流程。
> 代码在 [`src/data/build-issue.ts`](../src/data/build-issue.ts)。

## 一切都为了一个信号：被多家报道 = 重要

排序的主信号是「一件事被几家媒体报道」。这个信号只有在**同一事件的多篇报道真的被聚成一簇**
时才有意义——聚类漏了，重要新闻的家数就是 1，和边角料同级；聚类误合了，两件不相干的事
会被当成一件重要的事顶上去。所以聚类的准确度不是锦上添花，它是排序能不能用的前提。

## 为什么不是朴素 Jaccard

最早试的是标题分词后直接算 Jaccard 重合度，不可用：`ai` 出现在大约一半的标题里，
而 `hugging`、`face` 只出现在少数几条里。同等对待这两类词，会让「都提到了 AI」的两条
无关新闻拿到和真正同源报道一样的分数。

改成 **IDF 加权**之后，高频词的贡献被压下去，罕见词的共现才算数——这正好对应人的直觉：
两条标题同时出现「Hugging Face」比同时出现「AI」信息量大得多。

## `CLUSTER_THRESHOLD = 0.18` 是量出来的，不是拍的

当时的做法：把 110 条真实标题两两算分，人工标注哪些是真的同源报道，然后看两组分数的分布。

| | 分数区间 |
|---|---|
| 真正的跨源同源对 | 0.155 – 0.187 |
| 唯一一组误配 | 0.169 |

**两个区间是重叠的**。这意味着不存在既不漏合又不误合的阈值——只能选一边。

选 0.18（贴着真值区间的上沿）是因为两种错误的代价不对称：漏合一次，读者看到两条独立的
新闻，观感正常；误合一次，页面上会出现「A 事件，另有 1 家报道」而那家报道的其实是 B 事件，
这是读者能一眼看出的错误。**宁可漏合**。

代价是每期大约只合并 1~2 组。看到「合并得好少」不是 bug，是这个取舍的预期结果。

## 为什么只和簇的代表条比，不和全部成员比

聚类时每个新条目只跟各簇的**代表条**算相似度。试过跟全部成员比，会出现链式合并：
A≈B、B≈C，于是 A 和 C 被放进同一簇，尽管 A 和 C 毫不相干。簇越大越容易继续吸附，
最后滚成一个什么都有的大簇。只比代表条把这条传递链切断了。

代表条由 [`sources.json`](../sources.json) 里的 `priority`（缺省 1）决定，
排序打平时也用它。

## `ITEMS_PER_SOURCE_IN_CATEGORY = 4` 的由来

这个配额是被真实的坏结果逼出来的：某个高产的链接博客一度占掉「社区/独立博客」12 个位置
里的 9 个，那一版页面读起来像一个人的时间线，而不是一份周刊。限制单源在单个分类里最多 4 条
之后恢复正常。

## 没有 `pubDate` 的条目直接丢弃

不是懒，是没有正确做法：不知道发布时间就无法判断它属于哪一期。留下它的话，每次出刊的
时间窗过滤都会把它放行，同一条会周复一周地重复出现。

## 要改这些参数，走这个流程

本仓库没有测试框架，`pnpm rebuild-issue` 就是选取逻辑事实上的回归手段：

```bash
pnpm rebuild-issue 1 --skip-translation   # 用第 1 期的原始窗口重算，不消耗 DeepL 额度
```

改任何参数之前先跑一遍留底，改完再跑一遍，逐期 diff `content/issues/00N.json`，
确认变化是想要的。`--skip-translation` 不能省——调参往往要跑很多轮，每轮都翻译会很快
把月额度烧光。

尤其是 `CLUSTER_THRESHOLD`：它是量出来的数字，**不要凭感觉调**。真要动，请在当前的历史
快照上重做一次上面那张分布表，而不是直接改常量看页面观感。
